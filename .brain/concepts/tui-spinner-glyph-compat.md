# 概念：fullscreen 卡顿排查：先压测组件，再查动画字符字体

## 触发场景
- pi 切到 `tuiMode = fullscreen` 后，会话滚动 / 渲染体感卡顿，怀疑是自定义工具渲染器拖慢了。
- 转轮用了盲文点阵（`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` 这类）。
- 在 Herdr 等第三方终端上跑 pi。

## ❌ 表现
- fullscreen 下体感卡，第一反应往往是「历史消息太多，每帧全量重算拖垮了」。
- 转轮那一行每隔约 90ms 整行抖一下。
- 盲文字符在部分终端掉进回退字体，**宽度超过一格**，把整行挤得重排。

## 🛠 解法

### 第一步：先压测自己的组件，别急着怪历史重算

用 pi 自己的 `renderLayoutFrame` 铺 2000 个折叠胶囊，量每帧耗时：

**实测（2026-10-19）**：每帧 **0.56ms**。60fps 预算是 16.7ms，这只占 4%。

结论：全量重算历史**不是**瓶颈。胶囊组件本身够快，卡顿要去别处找。

### 第二步：真凶更可能是动画字符的字体兼容

盲文点阵转轮 `⠋⠙⠹…` 在 Herdr 等终端上走**回退字体**：

1. 回退字体的盲文字符宽度超过一格；
2. 转轮每 90ms 换一帧，每帧都把那一行挤得重排；
3. 用户看到的就是「整行每 90ms 抖一下」，体感等于卡顿。

**修法**：换成几何字符 `◐◓◑◒`。这几个是终端自带字体能画、宽度一格的字符，
不会掉进回退字体，也就不会把行挤宽。

```ts
// 原：⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏
const FRAMES = ["◐", "◓", "◑", "◒"];
```

### 排查顺序记法
先量（压测组件），再猜（动画字符 / 终端字体 / 滚轮事件延迟）。
反着来就会把精力花在优化一个不是瓶颈的东西上。

## 验证
- **压测判据**：`renderLayoutFrame` 铺 2000 个折叠胶囊，每帧耗时远小于 16.7ms
  （实测 0.56ms）。数字达标 → 组件不是瓶颈。
- **字形判据**：换 `◐◓◑◒` 后，在之前会抖的终端（Herdr）上看转轮是否还整行抖。
  2026-10-19 改完时这一步留待真机确认，当时未回填结论。
